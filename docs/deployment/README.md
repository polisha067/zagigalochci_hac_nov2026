# Размещение на недорогом VPS и последующие обновления

Подготовлен вариант для одного Linux VPS: FastAPI, SQLite на постоянном томе, Caddy для HTTPS и статической сборки фронта. Ollama/Qwen в этот комплект не входит. Конфигурация Compose проверена, но сборка и запуск контейнеров на реальном сервере пока не выполнялись: сервер/домен ещё не приобретены, локальный Docker daemon не запущен.

## Выбор сервера

Для небольшого демо: 1 CPU, желательно 2 GB RAM, SSD от 20 GB, Linux Ubuntu/Debian, публичный IPv4. 1 GB — тесный минимальный вариант, его нужно проверять нагрузкой; размещение Qwen3:8b в эти ресурсы не входит.

Ценовой ориентир на 08.11.2026: FirstVDS опубликовал московские тарифы «Прогрев» SSD от 299 ₽/мес и «Старт» SSD от 519 ₽/мес ([официальные цены с 01.07.2026](https://firstvds.ru/blog/s-1-iyulya-povysitsya-stoimost)). Итоговую конфигурацию, наличие, включённый IPv4 и дополнительные услуги нужно проверить в заказе; это не утверждение об уже выбранном и оплаченном сервере. Домен оплачивается отдельно, обычно за год; проверить и регистрацию, и продление.

Для существующей отправки через Яндекс необходимо исходящее соединение с `smtp.yandex.ru:465` (SSL). До оплаты уточнить возможность этого подключения у хостера. Это особенно существенно: [Timeweb Cloud по умолчанию блокирует 465/587](https://timeweb.cloud/docs/cloud-servers/limitations), а [бесплатные веб-сервисы Render блокируют SMTP и не имеют постоянного диска](https://render.com/docs/free).

## Что сохраняется при обновлении

- Исходники и каталоги данных — новая версия приложения из Git.
- База пользователей, сессии, коды и база наблюдений — постоянный том `backend-data`, путь `/var/lib/transport`.
- SMTP-реквизиты и постоянный `VERIFICATION_SECRET` — `deploy/.env` на сервере, вне Git и Docker image.
- Сертификаты HTTPS — отдельные постоянные тома Caddy.
- Фронтенд — собранные Искандером файлы в `deploy/frontend-dist`.

Обновление кода само по себе не удаляет эти тома. Не менять имя проекта/томов между выпусками и не выполнять `docker compose down -v`: этот флаг удаляет постоянные тома. В локальном Git уже исключены `.env`, исходные локальные БД и резервные копии; `.dockerignore` исключает их и из контекста сборки.

## Первый запуск

Нужны установленный Docker Engine с Compose plugin, доступ по SSH и права запуска Docker. Секреты в чат не пересылать. Ниже команды для корня репозитория; выполнить их на сервере после сохранения нужной версии кода в удалённой ветке.

1. Создать DNS A-запись домена на IP сервера. Порты 80/443 должны быть доступны для сайта и выпуска сертификата. Caddy автоматически получает и продлевает сертификат при корректных DNS/сетевых настройках ([документация](https://caddyserver.com/docs/automatic-https)).
2. Клонировать репозиторий и выбрать согласованный выпуск ветки `backend`.
3. Скопировать `deploy/.env.example` в `deploy/.env`. Указать реальный `DOMAIN` и `ALLOWED_ORIGINS=https://тот-же-домен`. `VERIFICATION_SECRET` сгенерировать один раз и сохранить; при обновлениях его не заменять. Для Яндекса указать существующий пароль приложения SMTP; для другого SMTP-провайдера заменить соответствующие поля. `APP_ENV=production`, `COOKIE_SECURE=true`, `MAIL_BACKEND=smtp` уже предусмотрены.
4. `chmod 600 deploy/.env`. Создать `deploy/frontend-dist`; когда фронт готов, положить туда содержимое его сборки, включая `index.html`.
5. Проверить и запустить:

```bash
mkdir -p deploy/frontend-dist
docker compose --env-file deploy/.env -f deploy/compose.yaml config -q
export RELEASE_TAG="$(git rev-parse --short HEAD)"
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d --build
```

API доступен на `https://домен/api`, документация — `/api/docs`, состояние — `/api/health`. Пока сборки фронта нет, главная страница может отвечать 404; API при этом можно проверять отдельно. Для фронта установить базовый адрес API `/api` и сохранить `credentials: "include"`. Один домен упрощает работу сессии в cookie. Данные не считаются перенесёнными с Mac автоматически: новая постоянная БД создаётся отдельно; импорт существующей базы требует согласованного переноса и резервной копии.

Сервер приложения работает в одном экземпляре, порт 8000 не публикуется наружу. Входящий трафик идёт через Caddy. Проверки Origin, JSON и запрет кеширования учитывают префикс `/api`.

## Отправка кодов пользователям

Сервер отправляет код на `email` каждого запроса регистрации. Всем участникам команды не нужны SMTP-пароли: настройка хранится один раз на общем сервере. Сайт работает при выключенном Mac, пока работает и оплачен VPS.

Текущая интеграция SMTP уже есть. После переноса надо проверить реальную цепочку регистрации на собственных адресах нескольких почтовых сервисов: письмо, подтверждение, вход и восстановление сессии. Само подключение к SMTP не гарантирует попадание каждого письма во входящие.

**Ящик `@yandex.ru` не следует обещать как постоянный транспорт для публичного потока пользователей.** Яндекс указывает ограничения SMTP и возможность блокировки однотипных писем; личные ящики не предназначены для массовых рассылок ([условия и ограничения](https://yandex.ru/support/yandex-360/customers/mail/ru/web/letter/create/send-many-letters)). Для общего запуска выбрать транзакционный почтовый сервис и подтвердить домен отправителя. Наш SMTP-клиент позволяет заменить провайдера через настройки. Цена почтового тарифа и условия бесплатного лимита проверяются отдельно; в стоимость VPS они не включены.

## Обновление кода и логики

Обычный цикл: изменения локально → тесты → commit/push согласованной ветки → сервер получает новую версию → пересборка и перезапуск. Перед обновлением создать резервную копию:

```bash
docker compose --env-file deploy/.env -f deploy/compose.yaml exec -T backend python /app/backup.py
git pull --ff-only origin backend
export RELEASE_TAG="$(git rev-parse --short HEAD)"
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d --build backend
docker compose --env-file deploy/.env -f deploy/compose.yaml ps
```

Резервная копия SQLite создаётся через SQLite backup API, включая записи в WAL, а не обычным копированием работающего файла. Копии внутри тома находятся в `/var/lib/transport/backups`. Для защиты от потери VPS скачать их на другую машину, например через `docker compose cp` и затем SSH/SCP. Сам `deploy/.env` тоже нужно безопасно сохранить отдельно: в копии SQLite его нет.

Обновление одного экземпляра может кратко прервать API. Изменение схемы БД требует совместимой миграции; копирование нового кода не заменяет её. Для возврата к старому выпуску использовать сохранённый Git commit/image tag. Откат приложения не откатывает схему/содержимое базы автоматически; при несовместимой миграции требуется восстановление заранее проверенной резервной копии при остановленном backend.

## Обновление данных

Каталоги сети и тарифов в версии проекта обновляются вместе с кодом; новая версия загрузится при перезапуске. Подтверждённые данные заменяют синтетические только после проверки единиц, срока действия, услуг и источников.

Импорт наблюдений и справочных снимков выполняется отдельно внутри работающего контейнера:

```bash
docker compose --env-file deploy/.env -f deploy/compose.yaml exec -T backend python -m backend.import_sources asop backend/data_sources/asop/observations.json
docker compose --env-file deploy/.env -f deploy/compose.yaml exec -T backend python -m backend.import_sources context backend/data_sources/rosmorport/references.json
docker compose --env-file deploy/.env -f deploy/compose.yaml exec -T backend python -m backend.import_sources context backend/data_sources/strategy/context.json
```

Скачанные большие исходные CSV/ZIP в Git не находятся: для их импорта сначала перенести файл на сервер/в контейнер и вызвать соответствующий импортёр. Пользователей повторно регистрировать при обычном обновлении не требуется.

## Проверено в этой подготовке

- Compose-конфигурация разбирается без настоящих секретов.
- Проверены защита API под `/api`, cookie-маршрут logout и адрес OpenAPI.
- Проверена консистентная копия SQLite при активном WAL.
- Полный набор тестов приложения запущен отдельно.
- Контейнерная сборка, выпуск публичного сертификата, сетевой доступ к SMTP и реальная доставка с VPS ещё требуют самого VPS и домена. Новых писем при подготовке не отправлялось.
