# Подтверждение почты и постоянная работа сервиса

## Пока ящика нет: локальная проверка

По умолчанию `MAIL_BACKEND=file`: сервер создаёт тестовые письма в
`backend/data/outbox/`. На настоящую почту ничего не приходит.
Коды не попадают в API, Swagger-ответы или журналы сервера.

1. Запустите сервер по [инструкции авторизации](AUTH.md).
2. В Swagger выполните `POST /auth/register` со своими тестовыми данными.
3. Сохраните `verification_id` из ответа 202.
4. В другом терминале, из корня репозитория, выполните:

   ```bash
   source .venv/bin/activate
   python -m backend.show_test_mail
   ```

5. Прочитайте код последнего письма и передайте **строкой** вместе с `verification_id`
   в `POST /auth/verify-email`. Успешный ответ — 200; браузер получит сессию.
6. Проверьте `GET /auth/me`.

Последнее письмо может относиться к другому адресу: перед вводом проверьте получателя.
Тестовые письма и локальный секрет находятся в исключённой из Git папке `backend/data`.
Локальный ящик — только для разработки, не для общего публичного сервера.

## Настоящие письма: вариант с отдельным ящиком Яндекса

1. Создайте отдельный ящик для проекта в Яндекс Почте. Его адрес станет отправителем.
2. В настройках почты откройте «Почтовые программы» и разрешите доступ почтовых
   клиентов и паролей приложений, как описано в [инструкции Яндекса](https://yandex.ru/support/yandex-360/customers/mail/ru/mail-clients/others).
3. В Яндекс ID создайте пароль приложения типа «Почта» с названием проекта.
   Обычный пароль аккаунта не используйте. По [инструкции Яндекс ID](https://yandex.ru/support/id/ru/authorization/app-passwords)
   активация пароля приложения может занять 2–3 часа.
4. Из корня репозитория, с активированным окружением, выполните:

   ```bash
   python -m backend.configure_mail
   ```

5. Укажите адрес ящика, сервер `smtp.yandex.ru`, защиту `ssl`, порт `465`,
   логин SMTP для своего ящика и пароль приложения. Для другого провайдера
   подставьте его настройки. Пароль вводится скрыто.
6. Перезапустите бэкенд и зарегистрируйтесь на **собственный адрес**, чтобы проверить
   доставку. При необходимости проверьте папку «Спам».

Настройки сохраняются в `backend/.env`, который сервер читает автоматически.
Файл исключён из Git. Не пересылайте его в чат и не публикуйте пароль приложения.
Настройки из окружения сервера имеют приоритет над `.env`.

Для замены только пароля без повторного ввода остальных полей:

```bash
python -m backend.configure_mail --password-only
```

Программа не сохраняет пустой пароль, переносы строк и нелатинские символы,
которые текущий SMTP-клиент не может передать при входе.

Параметры, которые сохраняет команда настройки:

| Переменная | Значение / смысл |
|---|---|
| `MAIL_BACKEND` | `smtp` — настоящая отправка; `file` — локальные письма |
| `MAIL_FROM` | Адрес отправителя, разрешённый вашим провайдером |
| `SMTP_HOST` | Для предложенного варианта `smtp.yandex.ru` |
| `SMTP_PORT` | Для SSL-варианта `465` |
| `SMTP_SECURITY` | `ssl` либо `starttls`; незашифрованный вход не поддерживается |
| `SMTP_USERNAME` | Логин почтового ящика для SMTP |
| `SMTP_PASSWORD` | Отдельный пароль приложения |

При ошибке передачи письма API вернёт 503 `mail_unavailable`, без технических
подробностей и секретов. Изменение кода откатывается: ранее действующий код
остаётся действующим до истечения срока. Ответ 202 при SMTP означает, что
почтовый сервер принял письмо, а не гарантирует попадание во входящие.

Реализация SMTP использует [стандартную библиотеку Python](https://docs.python.org/3/library/smtplib.html).

## Что значит «работает постоянно»

Почтовый ящик сам по себе не запускает бэкенд. Сейчас бэкенд работает на компьютере
Андрея: при остановке процесса или выключении компьютера API недоступен.

Для общего постоянного сервиса нужно разместить бэкенд на сервере/хостинге:

1. Запускать приложение автоматически после перезапуска и при сбое процесса.
2. Подключить публичный адрес и HTTPS, разрешить только адреса вашего фронтенда в CORS.
3. Передать SMTP-настройки в секреты окружения хостинга.
4. Задать `APP_ENV=production`, `COOKIE_SECURE=true`, `MAIL_BACKEND=smtp`
   и постоянный `VERIFICATION_SECRET` длиной минимум 32 символа.
5. Хранить SQLite на постоянном диске, а не во временной файловой системе контейнера.
   Сохранять резервные копии. Текущий вариант рассчитан на один общий экземпляр базы.
6. Разместить фронт и API в пределах одного сайта либо отдельно согласовать схему cookie.

Секрет можно сгенерировать локально:

```bash
python -c 'import secrets; print(secrets.token_hex(32))'
```

Не меняйте его при каждом запуске: он защищает коды подтверждения.
В development без явно заданного секрета приложение создаёт отдельный постоянный
файл `backend/data/verification.key`. При смене секрета старые коды нужно запросить заново.
В production тестовый почтовый режим и отсутствие секрета запрещены настройками приложения.

Хостинг и домен в текущей задаче не настроены. Выбор и публикация сервиса — отдельный шаг.
Доставляемость и лимиты отправки зависят от провайдера; отдельный ящик подходит
для первого прогона, а при росте отправок стоит подключить сервис транзакционных писем.
