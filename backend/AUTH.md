# Авторизация: инструкция для Андрея и Искандера

## Запуск сервера

Из корня репозитория, Python 3.9+:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r backend/requirements.txt
python -m uvicorn backend.app.main:app --reload --host 127.0.0.1 --port 8000
```

Если окружение уже создано и зависимости установлены, достаточно второй и последней команд.
В Windows активация: `.venv\Scripts\activate`.

- Базовый адрес API: `http://localhost:8000`.
- Интерактивная документация и проверка запросов: `http://localhost:8000/docs`.
- Машиночитаемый контракт: `http://localhost:8000/openapi.json`.
- Проверка работы сервера: `GET /health` → `{"status":"ok"}`.

SQLite создаётся автоматически в `backend/data/auth.sqlite3` и не попадает в Git.
Аккаунты и сессии сохраняются между перезапусками сервера. Не удаляйте файл базы,
если хотите сохранить пользователей. Тесты работают с отдельными временными базами.

## Контракт для фронтенда

Все запросы регистрации и входа — `Content-Type: application/json`.
Для **каждого** запроса авторизации используйте `credentials: "include"`.

| Метод | Путь | Что передать | Успешный ответ |
|---|---|---|---|
| POST | `/auth/register` | `name`, `email`, `password` | 201, `{ "user": ... }`, установлена cookie |
| POST | `/auth/login` | `email`, `password` | 200, `{ "user": ... }`, установлена новая cookie |
| GET | `/auth/me` | Только cookie | 200, `{ "user": ... }` |
| POST | `/auth/logout` | Только cookie, тело не нужно | 204, пустой ответ, cookie и сессия удалены |

**Регистрация сразу выполняет вход.** Дополнительный login после неё не нужен.
Выход повторяемый: если сессии уже нет, ответ всё равно 204.

### Регистрация

```json
{
  "name": "Андрей",
  "email": "andrey@example.com",
  "password": "choose-your-own-password"
}
```

Ограничения:

- Имя: 2–80 символов после удаления пробелов по краям.
- Email: корректный адрес, до 254 символов; пробелы по краям удаляются,
  регистр приводится к нижнему для поиска и уникальности аккаунта.
- Пароль: 8–128 символов; пробелы в пароле не удаляются.
- Неизвестные поля запроса отклоняются. Подтверждение пароля проверяет фронтенд,
  поле `password_confirmation` сервер не принимает.

Пример ответа (id и дата каждый раз другие):

```json
{
  "user": {
    "id": "a2072505-c58b-4fe3-b72e-cf0fe056a3f9",
    "email": "andrey@example.com",
    "name": "Андрей",
    "created_at": "2026-11-07T12:00:00Z"
  }
}
```

У login и me такая же структура ответа. В ответах нет пароля или токена сессии.

### Ошибки

Формат ошибок авторизации:

```json
{
  "error": {
    "code": "invalid_credentials",
    "message": "Неверная почта или пароль",
    "fields": []
  }
}
```

| HTTP | `error.code` | Что делать на фронте |
|---|---|---|
| 401 | `invalid_credentials` | Показать ошибку входа |
| 401 | `not_authenticated` | Показать форму входа; для первого me это нормальный сценарий |
| 409 | `email_already_registered` | Предложить войти с этой почтой |
| 422 | `validation_error` | Показать ошибки из `fields` |
| 429 | `too_many_attempts` | Подождать число секунд из заголовка `Retry-After` |
| 403 | `origin_not_allowed` | Проверить настройку адреса фронтенда |
| 415 | `json_required` | Отправлять JSON, не FormData и не HTML form |

Для 422 поле `fields` имеет вид:

```json
[{"field":"password","message":"Value error, Пароль должен содержать от 8 до 128 символов"}]
```

Сообщения отдельных проверок могут быть на английском. Для русских подписей
можно сопоставить `field` с полем формы. Введённые значения, включая пароль,
не возвращаются в ошибках проверки.

Сетевая ошибка `fetch` означает, что сервер недоступен или адрес/CORS настроен неверно;
её нужно обрабатывать отдельно от ответа HTTP 401.

### Пример подключения

Готовая обёртка: [`examples/auth-client.js`](examples/auth-client.js).
Её можно перенести во фронтенд и импортировать:

```javascript
import { createAuthClient } from "./auth-client.js";

const auth = createAuthClient("http://localhost:8000");

// После отправки формы регистрации:
const { user } = await auth.register({
  name: "Андрей",
  email: "andrey@example.com",
  password: "choose-your-own-password",
});

// Вход существующего пользователя:
await auth.login({
  email: "andrey@example.com",
  password: "choose-your-own-password",
});

// При загрузке страницы: 200 — восстановить пользователя, 401 — показать вход.
try {
  const { user } = await auth.me();
  console.log(user.name);
} catch (error) {
  if (error.status !== 401) throw error;
}

await auth.logout();
```

Cookie называется `a1_session`, имеет `HttpOnly` и `SameSite=Lax`.
JavaScript не должен читать её или сохранять токен в localStorage.
Сессия действует 7 дней от входа; срок не продлевается от просмотра страницы.
Выход отзывает текущую сессию на сервере. Вход обновляет сессию этого браузера,
остальные устройства остаются авторизованными.

## Адреса и настройки

По умолчанию разрешены фронтенды на `localhost` и `127.0.0.1` с портами 5173 и 3000,
а также адрес сервера с портом 8000 для Swagger. Используйте одинаковое имя хоста
для фронта и API: например, везде `localhost`. Не смешивайте `localhost` и `127.0.0.1`.

Если нужен другой адрес фронтенда, укажите его **точно**, включая схему и порт:

```bash
ALLOWED_ORIGINS=http://localhost:5174,http://localhost:8000 python -m uvicorn backend.app.main:app --reload
```

Шаблон переменных: [`.env.example`](.env.example). Файл `.env` автоматически
не читается; передавайте переменные через окружение процесса.

Искандер может запустить свою копию бэкенда локально. `localhost` на его компьютере
обращается к его серверу, а не к компьютеру Андрея.
Для общей проверки в доверенной локальной сети сервер можно запустить с
`--host 0.0.0.0`, а во фронте указать IP машины с сервером. В ALLOWED_ORIGINS
тогда нужен точный адрес страницы фронта. Не пересылайте рабочие пароли через HTTP.

В production задайте `APP_ENV=production`, `COOKIE_SECURE=true`, HTTPS и явный
список разрешённых адресов. Текущая cookie рассчитана на фронт и API в пределах
одного сайта (локально — одинаковый хост с разными портами). Размещение на разных
независимых доменах потребует отдельной настройки cookie и защиты запросов.

## Что реализовано и что дальше

- Пользователи и сессии хранятся в SQLite.
- Пароли хешируются Argon2; в базе хранится только SHA-256 хеш случайного токена сессии.
- Для неизвестного email и неверного пароля ответ одинаковый.
- Изменяющие запросы с чужим Origin отклоняются, формы входа принимают только JSON.
- Лимиты с одного IP: 10 попыток входа или 5 регистраций за 15 минут,
  включая успешные запросы. Счётчики сохраняются в базе. Параллельные запросы
  учитываются атомарно. За общим прокси IP нужно настроить корректно;
  произвольному `X-Forwarded-For` приложение само не доверяет.
- `require_user` в `app/main.py` готов для защиты будущих личных расчётов через Depends.

Расчётный модуль пока запускается отдельно; HTTP API расчётов и сохранение
истории пользователей ещё не подключены. Подтверждение почты, восстановление
пароля и вход через внешние сервисы пока не реализованы.

Реализация хеширования опирается на [документацию FastAPI](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/),
настройка браузерных запросов — на [документацию CORS](https://fastapi.tiangolo.com/tutorial/cors/).
В этом проекте используются серверные сессии, а не JWT из примера документации.

## Тесты

```bash
python -m pip install -r backend/requirements-dev.txt
python -m unittest discover -s backend -p 'test_*.py' -v
```

Тесты проверяют регистрацию, вход, нормализацию email, дубликаты, выход и отзыв
сессии, её истечение и сохранение при перезапуске, независимость пользователей,
хеширование, CORS/Origin, ошибки без пароля, лимиты запросов и Secure-cookie.
