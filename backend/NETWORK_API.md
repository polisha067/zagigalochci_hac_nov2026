# API сетевого расчёта для Искандера и Даши

> Речной сценарий Красноярск ↔ Дудинка: опубликованные компонентные тарифы + явно заданные синтетические условия. Подключение и формулы — [RIVER.md](RIVER.md).


> Авиация ЧукотАВИА: опубликованные тарифы и плановые рейсы подключены отдельным методом и к общему `/calculations` с `engine: "chukotavia"`. Формулы и ограничения — [AVIATION.md](AVIATION.md). «Аэрогруз» не используется.


Контракт ответа `schema_version: "0.3"`, версия HTTP-приложения `0.5.0`. Расчёты доступны гостям. История аккаунта использует HttpOnly-cookie после подтверждения почты или входа.

## Методы

| Метод | Назначение |
|---|---|
| `GET /network/options` | 7 категорий, хабы, существующие услуги, типы груза и упаковки, версия сети, пределы расчёта и отдельно состояние импорта наблюдений. |
| `POST /network/calculations` | Новый сетевой расчёт. |
| `GET /network/statistics/asop` | Агрегаты АСОП: фильтры по показателю, году, периоду и исходному PDF; спорные строки исключены по умолчанию. |
| `GET /network/sources` | Реестр 31 предоставленного источника со статусом проверки и назначением. Не следует путать с источниками конкретного кандидата. |
| `POST /calculations` | При `engine: "network"` принимает тот же новый запрос. Без этого поля остаётся прежний контракт трёх схем. |
| `GET /calculation-options` | Прежние списки для старой формы плюс ссылка на новый сетевой API. |

Тестировать можно до фронта в `http://localhost:8000/docs`. Выбрать `/network/calculations` → Try it out → вставить [network-request.json](examples/network-request.json) → Execute. Требуется действующая сессия. Все хабы примера учебные; их нельзя подписывать реальными городами.

## Запрос

Минимальный рабочий пример целиком лежит в `examples/network-request.json`; вариант четырёх видов — `examples/network-four-modes.json`.

| Поле | Значение |
|---|---|
| `engine` | Обязательно `"network"`. |
| `network_id` | Из `/network/options`, по умолчанию `synthetic-network-v1`. |
| `origin_hub_id`, `destination_hub_id` | Конкретные разные хабы из каталога. |
| `cargoes` | 1–20 позиций: `id`, введённое пользователем `name`, `weight_tonnes`, упаковка/делимость и необходимые свойства. `cargo_type` необязателен и оставлен для совместимости. Недостающие описание/упаковка/делимость возвращаются как уточнения. См. [CARGO_INPUT.md](CARGO_INPUT.md). |
| `pickup_hub_id`, `delivery_hub_id` внутри позиции | Промежуточные погрузка/выгрузка. По умолчанию начало/конец маршрута. |
| `ready_offset_hours` внутри позиции | Смещение её готовности относительно каждого момента отправки в плане. |
| `max_delivery_hours` внутри позиции | Индивидуальный предел вместо общего; срок годности всё равно учитывается. |
| `schedule` | Разовая: `{ "mode":"once", "ready_at":"2026-11-09T08:00:00+03:00" }`. Также прежние `regular` и `explicit`, см. ниже. |
| `max_delivery_hours` | Произвольное положительное число часов, например 36 или 2.5; не строка «2 дня». |
| `capacity_basis` | Обязательно `mass_and_volume` или явно выбранный `mass_only`. Для авиа объём обязателен в обоих режимах. |
| `cost_basis` | `including_vat` или `excluding_vat`; сравнение только на одной налоговой базе. |
| `data_policy` | `verified_only` требует фактов; `allow_assumptions` позволяет видимые оценки/синтетику. Неизвестные данные не превращаются в подтверждённые. |
| `service_ids` | Необязательный явный маршрут из существующих направленных услуг. |
| `required_modes` | Необязательная **точная последовательность**, например `["road","sea","air"]`, а не набор предпочтений. |
| `via_hub_ids` | Обязательные промежуточные хабы в порядке посещения. |
| `group_sizes` | Размеры проверяемых групп консолидации, например `[1,2,4]`; по умолчанию `[1]`. |
| `max_legs`, `max_paths` | Ограничения поиска, по умолчанию 6 этапов и 16 путей; максимумы 12 и 32. |

Регулярный план:

```json
{"mode":"regular","start_at":"2026-11-09T08:00:00+03:00","end_at":"2026-12-07T08:00:00+03:00","frequency":{"count":2,"unit":"week"}}
```

Явные готовности:

```json
{"mode":"explicit","ready_at":["2026-11-09T08:00:00+03:00","2026-11-12T15:00:00+03:00"]}
```

Если пользователь написал «регулярно по 10 т», ИИ должен уточнить частоту. Неизвестные города, грузы и тарифы нельзя подменять учебными id. Пользовательские ставки запрос не принимает: каталог проверяется на сервере.

## Ответ и отрисовка

Полные ответы восстанавливаются командой `python -m backend.export_examples --kind examples` в `backend/data/generated/examples/`. Отдельные копии каждого ответа в Git не хранятся.

- `shipments`, `total_volume_tonnes` — общий план. Это сценарный объём, не обученный прогноз.
- `network_id`, `network_fingerprint`, `coverage`, `request` — контекст воспроизведения.
- `candidates` — реальные строки таблицы альтернатив. У каждой: id, последовательность услуг/видов, размер группы, `status`, `complete`, цена за план/тонну, фактический максимальный срок, причины, источники, уровни подтверждения.
- `steps` — шкала перевозок и обработки с датами, массой на этапах и ожиданием. `deliveries` — контроль каждой исходной позиции. `cost_items` — расшифровка цены.
- `recommendation` — id лучшего допустимого кандидата, либо `null`.
- `categories` — **семь пересекающихся групп**. Мультимодальная цепочка может одновременно входить в авто, море и авиа. Не нужно рисовать её как четыре независимых услуги или суммировать группы.
- `warnings`, `assumptions`, `search` — видимые ограничения. `search.truncated=true` означает неполный поиск.

Статусы кандидата:

| Статус | Что показать |
|---|---|
| `feasible` | Допустим при заданных данных и принятой модели; `complete=true`. |
| `infeasible` | Нарушено известное условие: срок, вместимость, совместимость и т.п. |
| `insufficient_data` | Не хватает конкретных сведений: тариф, переход, коэффициент, допуск и т.п. |

У двух последних итоговые цены `null`. Нельзя показывать их как 0 руб. Частичные `steps`/`cost_items` объясняют, где остановился расчёт; они не являются полной стоимостью.

Если кандидатов нет, текст — «В загруженной сети при этих условиях вариант не найден». Это не доказательство отсутствия сообщения по России. Категория `not_confirmed_in_loaded_network` тоже не означает, что вид вообще не существует.

## Ошибки и лимиты

401 — нужна сессия; 403 — посторонний Origin; 415 — нужен JSON; 422 — некорректный запрос/неизвестные идентификаторы; 429 — общий лимит 30 расчётов в минуту на пользователя для старого и нового методов. Деловая невозможность маршрута возвращает 200 с причинами в кандидатах.

Расчёт ограничен 64 отправками × 20 позиций, максимум 32 пути × 4 группы. Для более длинного плана нужен другой режим/фоновый расчёт, а не удаление части отправок.

ИИ получает тот же ответ, по которому фронт строит таблицу. Если меняется вес или срок, обновить сохранённый запрос и вызвать сервер заново; не пересчитывать цену в тексте модели.

## Запуск без UI

Из корня репозитория после установки `backend/requirements.txt`:

```bash
python -m backend.run_network
python -m backend.run_network --request backend/examples/network-four-modes.json
python -m unittest discover -s backend -p 'test_*.py'
python -m uvicorn backend.app.main:app --reload
```

Это отдельное ядро не меняет регистрацию и SQLite пользователей. Сетевой каталог сейчас JSON; открытые наблюдения — отдельная SQLite. История аккаунта сохраняется в SQLite через `/auth/history`. Гостевая история хранится в браузере.


Статистика АСОП: `period_kind=year` или `Q1`, `include_flagged=false` по умолчанию. Перед суммированием нужно выбрать `source_file_id`: повторные публикации одного периода сохранены. Подробнее и пример импорта — [data_sources/asop/README.md](data_sources/asop/README.md).


## Уточнение описания груза

`input_status=needs_clarification` и `clarifications` означают, что сервер принял имя, но ждёт конкретных свойств. `candidates=[]`, `recommendation=null`; фронт показывает вопросы по `cargo_id`. Повторный запрос отправляется с тем же именем и добавленными ответами. При `input_status=ready` смотреть статусы кандидатов: доступность услуги всё ещё проверяется отдельно. Основной пример формы: [network-free-cargo-request.json](examples/network-free-cargo-request.json).

Регулярность теперь допускает `minute`, `hour`, `day`, `week`, `month` и целое `every`. Например две отправки каждые три дня: `count=2,every=3,unit=day`; каждые полтора часа: `count=1,every=90,unit=minute`. Точные даты задаются через `explicit`.
