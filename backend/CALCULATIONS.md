# Расчёт для фронтенда — контракт 0.2

## Запуск и доступ

Из корня репозитория:

```bash
source .venv/bin/activate
python -m pip install -r backend/requirements.txt
python -m uvicorn backend.app.main:app --reload
```

Swagger: `http://localhost:8000/docs`, раздел **«Расчёты»**.
Нужна действующая сессия подтверждённого пользователя: [AUTH.md](AUTH.md).
Все запросы фронта передают `credentials: "include"`.

| Метод | Адрес | Назначение |
|---|---|---|
| GET | `/calculation-options` | ID набора, доступные города, типы грузов и технические ограничения |
| POST | `/calculations` | Проверка запроса, расчёт трёх схем, источники, причины и рекомендация |

POST принимает только JSON. Тарифы клиент не передаёт: они загружаются из серверного
`examples/catalog.json` или файла, указанного в `CALCULATION_CATALOG_PATH`.
Демо-каталог полностью синтетический. Настоящие ставки ещё нужно собрать и подтвердить.
HTTP 200 означает, что запрос обработан; отдельные схемы могут быть недопустимыми или нерассчитанными.
Результаты пока не сохраняются в истории. Таблица пользователей для расчётов не изменяется.

## Минимальный запрос

```json
{
  "dataset_id": "synthetic-pilot-v2",
  "route": [
    {"city": "Москва", "service_hours": 0},
    {"city": "Брянск", "service_hours": 0}
  ],
  "cargoes": [
    {
      "id": "flour-1",
      "cargo_type": "flour",
      "weight_tonnes": 10,
      "load_at": 0,
      "unload_at": 1,
      "splittable": true
    }
  ],
  "schedule": {
    "mode": "regular",
    "start_at": "2026-11-09T00:00:00+03:00",
    "end_at": "2026-12-07T00:00:00+03:00",
    "frequency": {"count": 2, "every": 1, "unit": "week"}
  },
  "max_delivery_hours": 48,
  "capacity_basis": "mass_only"
}
```

Файл: [`examples/calculation-request.json`](examples/calculation-request.json).
Полный образец ответа: [`examples/calculation-response.json`](examples/calculation-response.json).
Результат: 8 отправок, 80 т; авто 240 000 ₽, договор 208 000 ₽,
ж/д цепочка 140 000 ₽ и 156 часов. При лимите 48 часов выбирается договор.
При увеличении лимита до 156 часов на том же условном наборе выбирается ж/д.

`capacity_basis` выбирается **явно**:

- `mass_only`: допускаются неизвестные объёмы; фронт показывает предупреждение о неполноте
  проверки. Уже известные объёмы и вместимость всё равно учитываются.
- `mass_and_volume`: у всех грузов нужен `volume_m3`, у перевозчика — вместимость в м³.

`splittable` — можно ли распределять позицию между транспортными единицами.
Для неделимых объектов программа не обещает укладку через простое деление тоннажа.

## Режимы расписания

Разовая перевозка:

```json
{"mode":"once","ready_at":"2026-11-09T09:00:00+03:00"}
```

Регулярная — через заданный интервал:

```json
{
  "mode":"regular",
  "start_at":"2026-11-09T09:00:00+03:00",
  "end_at":"2026-12-07T09:00:00+03:00",
  "frequency":{"count":1,"every":2,"unit":"week"}
}
```

Это раз в две недели. `count=2, every=1, unit=week` — два раза в неделю,
равномерно, с интервалом 3,5 дня. Единицы: `day`, `week`, `month`.
Дробная средняя частота задаётся целым числом за больший интервал:
2,5 раза в неделю → `count=5, every=2, unit=week`.
Для регулярных дней недели и рабочего календаря используйте конкретные даты:

```json
{
  "mode":"explicit",
  "ready_at":["2026-11-09T09:00:00+03:00","2026-11-13T14:00:00+03:00"]
}
```

Все даты обязаны содержать часовой пояс. Повтор одного момента с разными смещениями
тоже считается дубликатом. Конец регулярного периода не включается.
Срок передаётся **в часах**: 2 дня → 48, 12 часов → 12; строки «2 дня» не принимаются.

## Остановки и несколько грузов

Порядок `route` — порядок посещения пунктов. `load_at` и `unload_at` — индексы,
начиная с нуля; если `unload_at` опущен, это последний пункт.
Каждый груз имеет уникальный id. Его масса и объём заданы **на одну отправку**.
Общий состав повторяется для всех дат расписания.
В `service_hours` передавайте обработку и ожидание, не включённые в сроки участков.
По умолчанию 0; это явно показывается как допущение.

Пример: [calculation-stops.json](examples/calculation-stops.json).
Образец ответа: [calculation-stops-response.json](examples/calculation-stops-response.json).
Москва → Калуга → Брянск: в Москве загружаем 10 т муки и выгружаем в Калуге;
там забираем 15 т сахара и доставляем в Брянск. Итог 25 т груза, но максимальная
загрузка участка 15 т: достаточно одной машины на 20 т. Движение 8 + 12 ч,
обработка 1 + 2 + 1 ч: срок самого долгого груза **24 ч**.
Разовое авто стоит 35 000 ₽, договор — 59 000 ₽ с недельным минимумом.
Для ж/д такой маршрут возвращает `insufficient_data`, а не цену прямого направления.

## Что читать из ответа

- `schema_version`, `dataset_id`, `data_status`: версия и происхождение.
- `request`: нормализованные параметры для воспроизводимости.
- `shipments`, `total_volume_tonnes`, `ready_at`, `volume_by_week`: календарный план.
- `load_profile`: масса/объём и активные позиции на каждом участке.
- `schemes`: три результата с постоянными ID `spot_road`, `contract_road`, `road_rail_road`.
- `recommendation`: ID подходящей схемы либо `null`.
- `assumptions`, `warnings`, `sources`: обязательны для показа пользователю.

В каждой схеме:

| Поле | Смысл |
|---|---|
| `status` | `feasible`, `infeasible`, `insufficient_data` |
| `reason`, `missing_fields` | Объяснение и конкретные недостающие данные |
| `total_cost_rub`, `cost_rub_per_tonne` | Стоимость за период и за тонну |
| `max_delivery_hours` | Максимальный срок от готовности до доставки |
| `physical_trips`, `paid_trips` | Фактические авторейсы и оплачиваемые рейсы, если применимо |
| `departures` | Число исходных отправок для авто, укрупнённых партий для ж/д |
| `breakdown_rub` | Компоненты полной стоимости, их сумма равна итогу |
| `details` | Оплата по неделям, сроки по грузам либо ж/д партии и их расписание |
| `savings_vs_base_rub`, `savings_vs_base_percent` | Экономия относительно базы, отрицательно при удорожании |

Отсутствующие показатели сериализуются как `null`, а не 0. Их нельзя рисовать
как бесплатную доставку. `feasible` относится к ограничениям модели, не заменяет
реальное подтверждение услуги. Для ж/д `physical_trips` — сумма машин подвоза
и развоза; число ж/д единиц смотрите в `details.batches[].units`.
Не сравнивайте это поле между схемами как единый показатель количества транспорта.

Готовый клиент: [`examples/calculation-client.js`](examples/calculation-client.js).
График строится из `volume_by_week`, таблица — из `schemes`, объяснение — из
того же ответа. Нельзя придумывать числа для строк с `insufficient_data`.

## Ошибки и ограничения

- 401: нет действующей сессии подтверждённого пользователя.
- 403: чужой Origin; 415: тело не JSON.
- 422 `validation_error`: некорректные поля или неизвестный параметр — ничего не игнорируется.
- 422 `calculation_error`: неизвестный dataset_id или слишком много событий расписания.
- 429: не более 30 расчётов за минуту на пользователя; пауза в `Retry-After`.

Технические пределы: 512 отправок, 12 пунктов, 20 позиций, 3660 дней периода;
даты 2000–2100 годов, положительный срок до 87 600 часов. Частота: 1–168 событий
за каждые 1–3650 дней/недель/месяцев. Масса/объём одной позиции до 1 000 000 единиц.
Эти пределы защищают размер расчёта и не являются правилами перевозчиков.

Неподдерживаемые данные (например, индивидуальные даты готовности каждой позиции,
временные окна получателя или требования к температуре в запросе) отклоняются как
неизвестные поля. Для пилота свойства выбранного груза должны быть проверены в каталоге
и условиях перевозчика. Мы не заявляем, что инструмент умеет любую реальную перевозку.

Матрица проверок: [EDGE_CASES.md](EDGE_CASES.md). Формулы: [FORMULAS.md](FORMULAS.md).

## Проверка без фронта

Без HTTP и без входа, для проверки формул:

```bash
python -m backend.run_calculation
python -m backend.run_calculation --request backend/examples/calculation-stops.json
```

Через Swagger: войдите через `/auth/login`, выполните `GET /calculation-options`,
затем `POST /calculations` с JSON из примера. Сессия того же браузера передаётся автоматически.
Формулы и HTTP используют один модуль, числа должны совпадать.
