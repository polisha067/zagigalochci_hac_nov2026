## Регистрация и вход — для фронтенда

Добавлен сервер FastAPI с SQLite и сессиями в HttpOnly-cookie.
Полный контракт для Искандера: **[backend/AUTH.md](backend/AUTH.md)**.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r backend/requirements.txt
python -m uvicorn backend.app.main:app --reload
```

Документация после запуска: `http://localhost:8000/docs`.
Регистрация теперь требует подтверждения почты: `POST /auth/register` возвращает
202 и `verification_id`, затем `POST /auth/verify-email` принимает id и код.
Повторная отправка — `POST /auth/resend-verification`.
Также доступны `POST /auth/login`, `GET /auth/me`, `POST /auth/logout`.
Фронт отправляет запросы с `credentials: "include"`.
Без настройки SMTP письма сохраняются локально. Просмотр: `python -m backend.show_test_mail`.
Настройка настоящей отправки и постоянной работы: **[backend/MAIL.md](backend/MAIL.md)**.

## Расчёт перевозок и формулы — версия 0.2

Добавлен **POST `/calculations`** с проверкой сессии. Данные для списков формы:
**GET `/calculation-options`**. Контракт и готовые JSON: [backend/CALCULATIONS.md](backend/CALCULATIONS.md).
Подробные формулы: [backend/FORMULAS.md](backend/FORMULAS.md).
Матрица ограничений: [backend/EDGE_CASES.md](backend/EDGE_CASES.md).

### Что учитывается

- Разовая, регулярная перевозка и список точных дат; произвольный положительный срок в часах.
- Неполные периоды, календарные месяцы, даты с часовыми поясами, исключённая правая граница.
- Несколько грузов, погрузка/выгрузка на промежуточных остановках и загрузка каждого участка.
- Вместимость по массе и объёму, делимость груза, совместимость и известные доступные мощности.
- Оплачиваемый минимум договорных рейсов за ISO-неделю, включая пустые/неполные недели по данному типу договора.
- Ж/д накопление, остаток, расписание, подвоз, терминалы, развоз и хранение.
- Источники, период действия тарифов, причины невозможности расчёта и видимые допущения.

### Основные формулы

Сначала строим реальные моменты готовности t_i. Для разовой перевозки S = 1;
для регулярной считаем только события внутри [начало, конец).
Для каждой позиции c: масса m_c, погрузка a_c, выгрузка b_c.

$$
S=|\{t_i\}|,\qquad M=\sum_c m_c,\qquad Q=SM
$$

Масса и объём на участке l:

$$
M_l=\sum_{c:a_c\le l<b_c}m_c,\qquad V_l=\sum_{c:a_c\le l<b_c}v_c
$$

Число машин фиксированного парка на весь маршрут:

$$
n=\max\left(1,\max_l\left\lceil\frac{M_l}{q_m}\right\rceil,
\max_l\left\lceil\frac{V_l}{q_v}\right\rceil\right)
$$

Проверка объёма обязательна в `mass_and_volume`. Режим `mass_only` допускает
неполные данные об объёме, но не игнорирует известное ограничение. Для неделимых
позиций формула сама по себе не доказывает размещение — нужен план укладки.

Разовые авто: R_l — движение одной машины по участку; F_p — дополнительная
плата за промежуточную остановку; h — полная обработка тонны груза.

$$
C_{spot}=Sn\sum_lR_l+Sn\sum_pF_p+hQ
$$

Договорные авто:

$$
N_{paid,w}=\max(N_{actual,w},N_{min,w})
$$

$$
C_{contract}=\left(\sum_lR_l\right)\sum_wN_{paid,w}+Sn\sum_pF_p+hQ+F_{contract}
$$

Срок до выгрузки позиции c: ожидание подачи W, движение T_l и обработка H_p.

$$
D_c=W+\sum_{l=0}^{b_c-1}T_l+\sum_{p=0}^{b_c}H_p,\qquad D_{actual}=\max_cD_c
$$

Ж/д: отправки объединяются в последовательные группы G_j, включая остаток.
Каждая группа должна достигать минимума и укладываться в доступную мощность.
Стоимость — сумма подвоза, ж/д, терминалов, развоза и хранения; срок — от
готовности исходной отправки, включая накопление и ожидание поезда.
Точный алгоритм и формулы: [FORMULAS.md, раздел 6](backend/FORMULAS.md).

Стоимость тонны и экономия:

$$
c_i=\frac{C_i}{Q},\qquad E_i=C_{spot}-C_i,\qquad E_{i,\%}=100\frac{E_i}{C_{spot}}
$$

Процент считаем только при положительной базе. Рекомендуем минимальную стоимость
среди допустимых схем. Если нет подходящей — `recommendation: null`.
Деньги считаются через Decimal, итог равен сумме показанных компонентов.

### Проверочный пример

10 т × 2 раза в неделю × 4 недели = 8 отправок, 80 т.
**Все цены, совместимость и мощности ниже синтетические.**

| Схема | За период | За тонну | Максимальный срок | Лимит 48 часов |
|---|---:|---:|---:|---|
| Разовое авто | 240 000 ₽ | 3 000 ₽ | 24 ч | Подходит |
| Договорное авто | 208 000 ₽ | 2 600 ₽ | 24 ч | Подходит |
| Авто → ж/д → авто | 140 000 ₽ | 1 750 ₽ | 156 ч | Не подходит |

Рекомендуется договор, экономия 32 000 ₽ (13,33%). При лимите 156 часов на
том же наборе выбирается ж/д схема. Это вывод **при заданных условиях**, не рыночная рекомендация.

Пример с остановкой: Москва → Калуга → Брянск, 10 т выгружаются в Калуге,
затем загружаются 15 т. Перевезено 25 т, но максимальная загрузка — 15 т,
поэтому достаточно одной машины на 20 т. Разовый маршрут стоит 35 000 ₽
при условных тарифах, срок — 24 ч. Для ж/д такого маршрута пока нет отдельной модели/тарифа.

### Границы реализации

Результат — сценарный план, **не прогноз по истории**. Нет оптимизации упаковки,
общего оборота автопарка и произвольного ж/д разбиения. Специальные требования
должны подтверждаться для пилота. Неподдерживаемые поля не игнорируются: 422.
Отсутствие данных — `insufficient_data`, известное нарушение — `infeasible`.
Даже `feasible` означает соблюдение ограничений модели при показанных допущениях.

Проверка без HTTP:

```bash
python -m backend.run_calculation
python -m backend.run_calculation --request backend/examples/calculation-stops.json
```

Старый `run_demo.py` оставлен как учебный пример 0.1; фронт использует новый контракт 0.2.
